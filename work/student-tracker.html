Student Tracker (Frappe)

Problem brief, user stories, backlog and Sprint 1 plan for an NGO student-count tracking tool.

🎓

Student Tracker (Frappe). A monthly student-count tracking tool for education NGOs and program teams like Dhwani Rural Information Systems, with history, audit trail and bulk CSV updates.

RoleAssociate Product Manager (problem-solving assignment)
UsersProgram coordinators and supervisors at education-focused NGOs
DeliverableProblem brief, user stories with acceptance criteria, wireframe, backlog and Sprint 1 plan, UAT plan, risks
ToolsClaude AI (scope drafting), ChatPRD (UAT scenarios)

At a glance

Problem

Teams need an accurate, current student count per school and month, with prior tallies to spot patterns.

Solution

A count-entry and history tool with validation, permissions, conflict detection, bulk upload and an audit trail.

Sprint 1 (2 weeks)

Login and roles, school list, count model, entry and edit with validation, history table, audit trail.

Problem Brief

● Who needs this and why?

This system is mostly intended for education focused NGO’s or program teams (such as those at Dhwani Rural Information Systems itself) and also to keep track of student enrollment on a regular basis.

● Goals & non‐goals

  • View and update the current student count for any school and month.
  • Access prior month-end tallies to easily identify patterns.

NON- Goals

  • Does not keep track of individual students' history or enrollment events.
  • Should not temper with the Dashboard aspect at all cost.

● Success metrics (pick 2–3 you can measure early).

  • User-Centric Metrics: Percentage of schools that provide monthly counts before the deadline.
  • Anomaly detection: percentage of major changes identified and resolved.
  • Update the success rate (no failures or errors).
  • Audit log completion and latency.

2) User Stories + Acceptance Criteria (must‐have)

Here i have used Cluad AI for the Scope.

  1. Create/Update Current Count for a Month (Program Coordinator)

As a Program Coordinator, I want to enter or update the current student count for a school for a selected month, so that accurate data is always available.

Acceptance Criteria:

Scenario: User updates the current count for a school and month

Given I am logged in with edit access to a school

When I select a school and month

And I enter a valid (positive integer) student count

And I click "Save"

Then the system records the new count

And logs the editor, timestamp, and value

And displays a confirmation message

  1. View Monthly History (Program Coordinator & Supervisor)

As a user, I want to view a history of previous months’ student counts for each school, so that I have context for changes over time.

Acceptance Criteria:

Scenario: User views history of current counts for a school

Given I have access to a school

When I navigate to its profile

Then I see a table showing each prior month

And each record displays the count, editor, and timestamp

  1. Bulk Refresh/Update from File (Program Coordinator)

As a Program Coordinator, I want to refresh/update the student counts via a simple spreadsheet upload, so that I can make bulk changes efficiently.

Acceptance Criteria:

Scenario: User uploads new student counts via CSV

Given I have edit permissions for multiple schools

When I upload a valid CSV file with school IDs and counts

Then the system updates all corresponding current counts

And any invalid entries are rejected with an error

And all changes are logged (by school, who, when, value)

  1. Simple Permissions Enforcement (Supervisor)

As a Supervisor, I want only authorized users to create or edit a school's current count, so that data integrity is maintained.

Acceptance Criteria:

Scenario: Unauthorized user tries to edit a current count

Given I am logged in without edit permission to a school

When I attempt to edit the current count

Then the edit UI is disabled or hidden

And any direct edit attempts are rejected with an error

  1. Concurrent Edits and Change Audit (All Editors)

As a user, I want to be warned if another edit has happened since I loaded the page, so that data does not get overwritten unintentionally.

Acceptance Criteria:

Scenario: Edit conflict detection

Given I load the edit page for a school's current count

And someone else updates that count before I save

When I try to save my change

Then the system warns me of a conflict

And requires confirmation to overwrite

  1. Validation and Error Handling (All Users)

As a user, I want clear errors if I enter invalid data, so that my mistakes don’t corrupt reporting.

Acceptance Criteria:

Scenario: Data validation on entry

Given I am editing or uploading a current count

When I enter a negative number, blank, or non-integer

Then the system rejects the input and displays a helpful error

● A small prioritized backlog (8–12 items) with rationale.

  • Login & Access Control – User authentication and school-level permissions (foundational for security, blocks all other work).
  • School List View – See all assigned schools; needed for navigation and task selection.
  • Current Count Data Model – Store per-month counts with audit fields.
  • Count Entry/Update UI (Single School) – Core feature: enter and edit “Current Count.”
  • Validation & Error Handling – Prevent bad data, ensure smooth workflow.
  • History Log/Timeline (Single School) – Review previous months, critical for transparency.
  • Bulk CSV Upload Flow – High-leverage for bulk updates (program coordinator).
  • Audit Trail Display – Display who-changed-what, builds trust.
  • Anomaly Warning (optional for Sprint 1) – Flag sharp drops/rises for supervisor review.
  • Responsive/Accessible Layout – Usability for low-connectivity/field staff.
  • Edit Conflict Detection – Prevent accidental overwrites.
  • Basic Analytics Export – Allow simple download of data for further analysis (low lift, high value).

● A one‐sprint outline (2 weeks): what you ship by the end of Sprint 1.

  • Login and role-based access control (basic).
  • School list view with navigation.
  • Current Count model and a functional single-school view.
  • Add/edit Current Count for any month, with inline validation and error messages.
  • Simple history count display (table below current value).
  • The audit trail shows who made what modifications and when.
  • UAT-ready: The main "happy path" and validation.

● UAT plan: 5 quick scenarios (happy path + edge).

Taken from chatprd.com

  • Happy Path - Program Coordinator checks in, chooses a school, enters a legitimate count, and sees the result stored and displayed.
  • Invalid Input - The user submits a negative or blank count; the system displays a clear error and prevents saving.
  • Bulk Upload - Coordinator uploads a CSV; correct rows are updated, while invalid rows display file-specific errors.
  • Permission Violation: A user without edit access attempts to update a count; the system neatly prevents the operation.
  • Concurrent Edit - One user initiates a count edit as another updates it; when saved, the system warns of a conflict and requests confirmation.

● Risks (top 3) with mitigations.

    1. Data Overwrites (Concurrency): Editing by several users at the same time may result in loss of changes.

Mitigation: Warn about identified modifications since page load; approve overwrite before saving.

    1. Adoption/Training Barriers: Non-technical workers may struggle with the UI and upload flow.

Mitigation: Include microcopy assistance; test with real users prior to launch; and provide a backup manual-input mode.

    1. Data Integrity (Permissions): Unauthorized modifications and data leaks can undermine confidence.

Mitigation steps include enforcing server-side rights, logging all changes, and reviewing permission logic in UAT.

Self-Assessment: Given another day, I would create a dispute resolution UI for offline sync circumstances and perform 2-3 user interviews with actual field coordinators to confirm our assumptions about their workflow preferences.
